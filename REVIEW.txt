## 3. Критичные проблемы

Критичных не выявлено. Проверено отдельно: сборка чистая; [Authorize] есть на всех
нужных страницах; чужие ID не открываются; падений при пустых данных не нашлось.

Ближайшие к критичным (чинить до защиты):

3.1. Посещаемость считает ещё не наступившие занятия
  Файл: Pages/Student/Index.cshtml.cs:62-68
  Описание: TotalLessons = количество ВСЕХ занятий группы (без фильтра по датам),
  Absences считается только по прошедшим (по фактическим отметкам).
  Последствия: процент посещаемости завышен; подпись «9 из 9 занятий», хотя
  будущие занятия ещё не были. На демо-данных разница ~3-5 п.п.
  Исправление: `await _db.Lessons.CountAsync(l => l.GroupId == student.GroupId
  && l.DateFrom <= DateTime.Now)` (одна строка).

3.2. Срок сдачи сравнивается с UTC, а хранится как локальная дата
  Файлы: Pages/Student/Homeworks.cshtml:59 (`hw.Deadline.Value < DateTime.UtcNow`),
         Pages/Teacher/Homeworks/Create.cshtml.cs:53 (`< DateTime.UtcNow.Date`),
         Pages/Teacher/Homeworks/Create.cshtml:38 (input type="date" → 00:00).
  Описание: Deadline приходит как дата (00:00, Kind=Unspecified), хранится как
  есть, а проверка «просрочено» идёт против UtcNow. В часовом поясе UTC+3
  дедлайн «сгорает» примерно в 03:00 дня дедлайна, а не в полночь/конец дня.
  Дополнительно: серверной проверки дедлайна при загрузке работы нет
  (Student/Homeworks.cshtml.cs:77-146) — UI пишет «Просрочено», но загрузить
  всё равно можно.
  Исправление: сравнивать с `DateTime.Now` / `DateTime.Today`, а по дате
  считать просрочку как `Deadline.Date < DateTime.Today`; при желании добавить
  ту же проверку в OnPostAsync (5 строк).

3.3. Подпись занятия в недельном календаре у студента и учителя наполовину пустая
  Файл: Pages/Shared/_WeekGrid.cshtml:29 — `@l.GroupName @ l.TeacherName`
  Описание: Student/Schedule.cshtml.cs:76-83 и Student/Schedule/Calendar.cshtml.cs:56-63
  заполняют только TeacherName; Teacher/Calendar.cshtml.cs:49-57 и
  Teacher/Index.cshtml.cs:71-79 — только GroupName. В итоге студент видит
  « @ Иванов И.И.», учитель — «ИС-22 @ ».
  Исправление: собирать строку в partial с учётом пустых частей
  (2-3 строки) либо заполнять оба поля.

## 4. Средние проблемы

4.1. Три страницы-дублёра календаря недостижимы из интерфейса
  Файлы: Pages/Admin/Schedule/Calendar.cshtml(.cs), Pages/Student/Schedule/Calendar.cshtml(.cs),
         Pages/Teacher/Calendar.cshtml(.cs)
  Описание: недельный календарь уже есть прямо в Index-страницах
  (Admin/Schedule/Index.cshtml:46-61, Student/Schedule.cshtml:45-60,
  Teacher/Index.cshtml:33-48). На сами Calendar-страницы не ведёт ни одна ссылка
  (проверены все asp-page в проекте), а их переключатель ведёт обратно на Index.
  Последствия: ~120 строк дублирующего кода, риск спросить «зачем они» на защите.
  Исправление: удалить эти 6 файлов или добавить ссылку на них.

4.2. Можно создать второе ДЗ на то же занятие
  Файлы: Pages/Teacher/Homeworks/Create.cshtml.cs:59-87 (проверки «уже есть ДЗ» нет),
         Pages/Teacher/Lesson.cshtml.cs:75 (берёт FirstOrDefault — покажет только первое),
         Pages/Teacher/Homeworks/Details.cshtml.cs:99-105 (снимает и перезаписывает
         ВСЕ оценки Type=Homework занятия, а не одного ДЗ).
  Последствия: при двух ДЗ на занятие у студента одна «Оценка за ДЗ» на занятие,
  страница занятия показывает не то ДЗ, сдача второго ДЗ не видна на странице занятия.
  Исправление: либо запретить второе ДЗ (ModelState-ошибка, 5 строк),
  либо (дороже) вести оценки по HomeworkId — для курсовой достаточно первого.

4.3. Смена группы у занятия с уже выставленными оценками
  Файл: Pages/Admin/Schedule/Edit.cshtml.cs:81-86
  Описание: GroupId меняется без проверки наличия оценок/ДЗ (для удаления такая
  проверка есть — Admin/Schedule/Index.cshtml.cs:86-91).
  Последствия: оценки прошлой группы остаются привязаны к занятию, но студенты
  новой группы их не видят; средний балл студентов старой группы продолжает
  включать это занятие; при следующем сохранении посещаемости учителем они
  будут удалены (Lesson.cshtml.cs:131-135).
  Исправление: запретить смену группы при наличии оценок (как при удалении).

4.4. Повторное сохранение посещаемости стирает оценки удалённых студентов
  Файл: Pages/Teacher/Lesson.cshtml.cs:131-140
  Описание: RemoveRange по всем Lesson/NA-оценкам занятия, создание заново —
  только для активных студентов (!IsDeleted). История soft-deleted студента
  по этому занятию теряется.
  Исправление: брать в RemoveRange только оценки активных студентов
  (добавить `studentIds.Contains(g.StudentId)` — как уже сделано в
  Teacher/Homeworks/Details.cshtml.cs:100-104).

4.5. Soft delete не разлогонивает уже открытую сессию
  Файлы: Pages/Account/Login.cshtml.cs:48-52 (проверка только при входе),
         страницы Student/Teacher IsDeleted не проверяют.
  Описание: при удалении пользователя активная кука остаётся. Снимание ролей
  обновит куку лишь при ближайшей валидации security stamp, поэтому до истечения
  срока/обновления куки удалённый пользователь может продолжать работать
  (данные он видит свои, чужие — нет).
  Исправление (необязательно для курсовой): при soft delete менять SecurityStamp
  (`await _userManager.UpdateSecurityStampAsync(user)`) — 2 строки.

4.6. Нет ограничения размера на файлы у учителя и на картинку объявления
  Файлы: Pages/Teacher/Homeworks/Create.cshtml.cs:66-78,
         Pages/Admin/Announcements/Create.cshtml.cs:50-63
  Описание: у студента лимит 10 МБ есть (Student/Homeworks.cshtml.cs:92-96),
  у учителя и админа нет (сработает только общий лимит multipart ~128 МБ).
  Проверки расширения/типа нет нигде — для курсовой допустимо, но лимит
  поставить стоит.

4.7. Удаление группы блокируется soft-deleted студентами
  Файл: Pages/Admin/Groups/Index.cshtml.cs:45
  Описание: `AnyAsync(u => u.GroupId == id)` без `!u.IsDeleted`.
  Последствия: группа, где остались только удалённые студенты, не удалится
  (ошибка «в ней есть студенты» — неверная).

## 8. Производительность

- N+1: не найдено. Проверены все страницы — запросов внутри циклов foreach нет
  (единственные совпадения — цикл по ошибкам ModelState, не по данным).
  Типовые «опасные» места сделаны правильно:
  - Admin/Users: один запрос с left-join на роли и группы (Users/Index.cshtml.cs:38-58);
  - Student/Grades: агрегация GroupBy на стороне БД (Grades.cshtml.cs:49-58);
  - Teacher/Journal: 5 запросов на всю таблицу (Journal.cshtml.cs:34-81);
  - Admin/Groups, Admin/Subjects: подсчёт через COUNT в проекции
    (Groups/Index.cshtml.cs:24-34, Subjects/Index.cshtml.cs:24-33).
- Лишние Include: не найдено — 11 Include в проекте, все навигации реально
  используются в представлениях.
- AsNoTracking: не используется ни разу. Для read-only страниц
  (списки занятий, оценки, объявления) это бесплатный выигрыш — можно добавить
  в 5-6 запросов. Не критично для объёмов курсовой.
- Лишние запросы: Admin/Index делает 8 последовательных count-запросов
  (Admin/Index.cshtml.cs:40-47) — можно объединить, но на LocalDB незаметно.
- Кэширование: не используется и не требуется (данные меняются часто, объёмы малы).
- Seed при каждом старте выполняет проверки `AnyAsync` — идемпотентно и дёшево.
- Итог: для курсовой производительность в порядке, мест для оптимизации — на
  «плюс» в пояснительной, а не в обязательные правки.

  SPEC.md:63.

  (SPEC.md:64), менять не нужно, достаточно упомянуть в пояснительной.

  «для чистоты» — явно запрещены SPEC.md:62.

  rate limiting, CSP, антибрут — SPEC.md:63, 164 считает настройки минимальными.
- Пагинация, кэширование (IMemoryCache/дистрибутив), профилирование, индексы
  БД, оптимизация запросов «на будущее» — данные учебные, объёмы крошечные.

  прямо запрещает.
- Тёмный режим, i18n/локализация, SPA/React/Vue, сложный JS, JS-библиотеки
  календарей — SPEC.md:66-67, 142.
- Обновление до свежих версий пакетов «заодно», рефакторинг «на глаз»,
  переименования без необходимости.
- Serilog/ELK, структурированное логирование, метрики, трейсинг — достаточно

- Исправление SPEC.md (в нём есть дубли и расхождения) — ТЗ менять не надо,
